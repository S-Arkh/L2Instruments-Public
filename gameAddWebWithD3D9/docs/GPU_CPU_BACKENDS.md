# GPU/CPU: статус интеграции по профилям

## Итог и принятое решение

Первоначально рассматривались основной прямой GPU-путь и выбираемый CPU-путь.
После проверки устройств отменена адаптация устройств и текстур
(2026-10-30: «нет, адаптацию устройств и текстур не нужно делать»).
Интеграция GPU в игровой рендерер остановлена; переключатель GPU/CPU не реализован.
Текущие out/high-five и out/gracia работают через WGC/D3D11 readback → CPU → UTexture.
Прямой D3D11 → D3D9Ex GPU-sharing сохранён как самостоятельный эксперимент.

## Какие реализации сохранены

| Вариант | Где находится | Передача изображения |
|---|---|---|
| Актуальный HF | `out/high-five/system` | WGC/D3D11 → RAM → игровая UTexture |
| Актуальная Gracia без helper EXE | `out/gracia/system` | WGC/D3D11 → RAM → игровая UTexture |
| Предыдущая Gracia с GraciaBrowserHost.exe | `profiles/gracia/result/system` | WGC/D3D11 → BGRA в общей памяти процессов → игровая UTexture |
| Самостоятельный GPU-прототип | `native/gpu_probe.cpp`, `build/Release/gpu_probe.exe` | Общая GPU-текстура D3D11/D3D9Ex на отдельно созданном устройстве |

Отсутствие helper EXE не означает отсутствие CPU-readback. Общая память
процессов в прежней Gracia не является общей GPU-текстурой. Оба способа
передают кадры; различается маршрут данных.

В GPU-прототипе используются CreateTexture с shared handle и OpenSharedResource.
Исторический отчёт: [d3d9ex-shared-probe.json](../reports/d3d9ex-shared-probe.json).
Путь сохранён при объединении проектов; пересборка находится в
`work/migration/gpu/Release/gpu_probe.exe`.
Отдельный эксперимент показал около 59,6 кадров/с на RTX 3080. Это не замер
GPU-браузера внутри HF/Gracia и не доказательство ускорения относительно CPU
в одинаковой игровой нагрузке. Прямой GPU-путь потенциально исключает readback
и повторную загрузку пикселей, но сравнительного игрового теста двух режимов нет.

## Проверка настоящего устройства игры, 2026-10-30

| Профиль | Прямой GPU на устройстве клиента | CPU |
|---|---|---|
| High Five | Устройство вернуло E_NOINTERFACE для IDirect3DDevice9Ex | Подтверждён |
| Gracia Epilogue | Устройство вернуло E_NOINTERFACE для IDirect3DDevice9Ex | Подтверждён |
| Scryde | Рабочая игровая интеграция браузера не получена | Исследование прекращено |

В HF и Gracia диагностический модуль подключён к запущенным установленным клиентам.
На реальном вызове EndScene получено:

```
QueryInterface_IDirect3DDevice9Ex=0x80004002
GetCreationParameters=0x00000000 adapter=0 behavior=0x00000142
```

Оба клиента вернули одинаковый результат выше и используют обычные D3D9-устройства.
Первоначальное сообщение об отсутствии процесса HF было ошибкой обнаружения:
неповышенному процессу был недоступен путь запущенного l2.exe. Подключение с
повышенными правами к PID 33484 успешно получило данные реального устройства HF.
Сохранённый
`native/gpu_probe.cpp` использует отдельно созданное D3D9Ex-устройство и не
является готовым адаптером рендерера игры. GPU-sharing того эксперимента
не подключается к текущему устройству Gracia простой заменой CopyFresh.

Для переноса именно этого GPU-прототипа потребовалась бы отдельная интеграция: создание совместимого
устройства, обработка ресурсов (в частности D3DPOOL_MANAGED несовместим с
D3D9Ex), привязка GPU-текстуры к конкретной игровой UTexture и обработка reset.
Потребовались бы также игровые проверки обоих режимов для каждого профиля.
Эти работы не выполнялись и отменены. Результат QueryInterface
доказывает отсутствие интерфейса D3D9Ex у проверенных устройств, а не невозможность
любых иных способов GPU-интеграции. Scryde этим экспериментом не проверялся.

### Сохранённые свидетельства

- [HF: отчёт устройства](../reports/renderer-device-high-five.json): PID 33484,
  успешное подключение, E_NOINTERFACE на реальном EndScene.
- [Gracia: отчёт устройства](../reports/renderer-device-gracia.json): PID 38724,
  успешное подключение, тот же результат.
- Исходные журналы: `work/renderer-probe/Release/renderer-33484.log` и
  `work/renderer-probe/Release/renderer-38724.log`.
- Исходники диагностики: `tools/renderer_probe/`; сборка Win32 MSVC прошла.

Диагностика не заменяла Core, ExtensionL2, графическое устройство или игровые
текстуры. Модуль наблюдения загружался в процесс; после завершения процесса
его перехват EndScene исчезает. CPU-комплекты не переводились в GPU-режим.

## Диагностический инструмент

`tools/renderer_probe/` содержит Win32 attach-инструмент и DLL наблюдения.
DLL создаёт временное тестовое устройство только для получения адреса EndScene,
освобождает его, затем наблюдает вызов на настоящем устройстве игры.
Данные пишутся рядом с DLL в renderer-<PID>.log. Способ отрисовки не заменяется.
После загрузки диагностической DLL её не выгружать из живого процесса:
завершить тестовый клиент. run.ps1 закрывает только запущенный им клиент указанного пути.

Пример из корня проекта:

```powershell
cmake -S tools/renderer_probe -B work/renderer-probe -G "Visual Studio 17 2022" -A Win32
cmake --build work/renderer-probe --config Release
.\tools\renderer_probe\run.ps1 -Profile gracia -ClientSystem 'C:\Games\Gracia\system'
```

Параметр `-ClientSystem` обязателен. Для внешней сборки укажите
`-BinaryDirectory 'C:\Build\renderer-probe\Release'`; `-Report` задаёт путь JSON.
Для наблюдения уже запущенного клиента есть `-AttachPid <PID>`; он не закрывает
этот процесс. При недоступном пути процесса диагностику нужно запускать с теми
же правами, что и клиент. После проверки завершите игру для выгрузки модуля.
MinHook берётся из соседнего int64/third_party/minhook.
Новые отчёты по умолчанию: `work/renderer-probe/renderer-device-<profile>-<timestamp>.json`.
Исторические отчёты в `reports/renderer-device-*.json` сохраняются без перезаписи.
