# Раздельные схемы и ленивая загрузка

## Организация

Встроенный каталог разделён на 25 файлов профилей в `schemas/`.
`schemas/index.json` содержит список файлов, подписи и порядок 26 пунктов меню.
Некоторые названия используют один профиль. Все 1362 описания структур и их
идентификаторы сохранены; формат XDAT и формат JSON-документа не изменены.

Разделение выполнено по формату XDAT, а не только по сетевому протоколу.
Например, Essence и Japan используют `essence_native.json`, Korea —
`korea_native.json`. Имя файла соответствует пространству имён его структур.

## Загрузка и кеш

`app/schema_catalog.py` предоставляет `SchemaRepository`:

- При запуске читает индекс встроенных схем, не их структуры. Метаданные файлов
  используются для отслеживания изменений.
- `text(schema)` загружает выбранный профиль и необходимые зависимости.
  Пространства имён включаются целиком, чтобы сохранить неявные полиморфные типы.
  Ссылки перечислений не считаются ссылками на отдельные структуры.
- Хранит разобранные пакеты и подготовленный JSON в LRU-кеше: по умолчанию
  не более трёх профилей. Кеш не хранит открытые XDAT или объекты `Document`.
- `refresh()` проверяет изменения индекса, профилей и пользовательских пакетов.
  При изменениях кеш сбрасывается; при неизменных файлах используется повторно.

Пользовательские пакеты сохраняют прежний самостоятельный JSON-формат. У них
нет отдельного индекса, поэтому при обнаружении они читаются и проверяются для
получения списка версий и обнаружения конфликтов идентификаторов. Это отличается
от индексной загрузки встроенных профилей.

Редактор передаёт C++-ядру только выбранный профиль с зависимостями. Открытый
документ владеет собственной схемой и не зависит от последующего вытеснения
профиля из кеша. Неудачное открытие не заменяет текущий документ и его изменения.

При импорте JSON `app/json_schema.py` потоково находит верхнеуровневое поле
`schema`, не создавая в Python копию всего дерева. Затем загружается профиль,
а полную проверку документа выполняет штатный JSON-импорт C++-ядра.

## Анализатор и инструменты

Автоопределение перебирает уникальные идентификаторы схем в прежнем порядке.
Каждый кандидат получает свой профиль; общий каталог для перебора не создаётся.
Прогресс, отмена и диагностика сохраняются. Ошибка загрузки отдельного профиля
отмечается в результатах и не останавливает проверку остальных кандидатов.

Это сокращает не только начальную загрузку: `Document::probe()` создаёт
временный документ из переданного каталога. Теперь при каждой проверке
копируется и разбирается один профиль, а не все встроенные схемы.

Исследование, создание черновика и экспорт работают с выбранным пакетом.
Импорт проверяет конфликты идентификаторов; установка и изменение пакета
обновляют реестр редактора. Команды с известной схемой и зависимые скрипты
также используют загрузку конкретного профиля.

Для генераторов и операций со всем каталогом остаются явные функции
`load_catalog()` и `catalog_text()`. Они собирают каталог в памяти; объединённый
`schemas.json` не хранится в репозитории. Самостоятельные внешние каталоги
по-прежнему поддерживаются.

В отчётах аудита поле `schema_hash_scope` указывает область хеширования:
`selected-profile`, `selected-profiles`, `source-file` или `catalog`.
Хеш выбранного профиля нельзя сравнивать с хешем всего прежнего каталога как
с равнозначным показателем.

## Замеры

Проверка выполнена на Windows x64, CPython 3.12.10, с одним реальным normal XDAT
профиля Essence/Japan размером около 7,5 МБ. Сравнивались два режима одного
инструмента: `eager` — полный каталог; `lazy` — `SchemaRepository`.

Для каждого режима выполнено пять запусков в отдельных процессах, сначала
`eager`, затем `lazy`, после завершения тестов. Файловый кеш ОС не очищался.
Это сравнение подготовки схем и операций ядра, а не времени запуска всего GUI.
Окружение и входной файл в обоих режимах одинаковые.

В таблице указана медиана, в скобках — минимум–максимум пяти запусков.

| Операция | Полный каталог | Ленивая загрузка |
| --- | ---: | ---: |
| Начальная загрузка каталога/индекса, мс | 71,63 (67,84–73,21) | 1,55 (1,49–2,21) |
| Первая загрузка выбранного профиля, мс | Уже включена в каталог | 9,43 (8,20–10,74) |
| Создание `Document`, мс | 121,67 (115,68–125,30) | 5,61 (5,26–6,81) |
| Подготовка схемы и `Document` суммарно, мс | 192,20 (187,82–198,52) | 16,31 (14,96–19,76) |
| Разбор XDAT из памяти, с | 7,29 (7,12–7,76) | 6,95 (6,05–7,70) |
| Повторное создание, разбор и освобождение документа, с | 7,40 (7,30–7,84) | 6,44 (6,31–8,27) |
| Полный перебор кандидатов, с | 16,68 (15,77–17,19) | 8,89 (8,67–10,83) |

Суммарная подготовка вычисляется для каждого запуска до расчёта медианы.
Попадание в кеш выбранного профиля в режиме `lazy` занимало менее 0,01 мс.
Чтение байтов XDAT с диска не входит в время его разбора. Повторное открытие
в замере использует уже прочитанные байты и включает освобождение временного
документа; оно не моделирует весь путь открытия через GUI.

Прирост пикового рабочего набора процесса от исходного состояния до создания
пустого `Document` составил **35 568 КиБ → 2 456 КиБ** по медиане
(примерно **34,7 МиБ → 2,4 МиБ**). Измерение выполнено через Windows
`GetProcessMemoryInfo`: это прирост пикового рабочего набора, а не точный счётчик
выделений схем и не общий расход памяти редактора с открытым XDAT.

Основной выигрыш относится к подготовке схем и перебору кандидатов. Диапазоны
времени разбора самого XDAT перекрываются; устойчивое ускорение этой операции
по пяти запускам отдельно не утверждается. Абсолютные значения зависят от
машины, сборки ядра и файла.

## Повторение замеров

Из каталога `interface_editor`, в PowerShell:

```powershell
$Sample = Read-Host 'Путь к локальному XDAT'
$Schema = 'essence_native.XDAT'
New-Item -ItemType Directory -Force local | Out-Null

.venv\Scripts\python.exe tools/benchmark_schemas.py --mode eager --sample $Sample --schema $Schema --repeat 5 --output local/schema-loading-eager.json
.venv\Scripts\python.exe tools/benchmark_schemas.py --mode lazy --sample $Sample --schema $Schema --repeat 5 --output local/schema-loading-lazy.json
```

В отчётах сохраняются числовые замеры и результаты проверки кандидатов, без
пути к исходному клиенту, его содержимого, имени пользователя или учётных данных.
Инструмент поддерживает Windows и Linux; на Linux пик памяти берётся из
`getrusage`, поэтому показатели памяти разных ОС не следует смешивать.

## Проверки корректности

- Сравнение при разбиении: все структуры, идентификаторы и порядок версий
  совпадают с прежним каталогом.
- Полный Windows-набор: **229 passed, 29 skipped, 20 subtests passed**.
- Проверены индексная загрузка, ограничение и сброс кеша, зависимости,
  пользовательские пакеты, JSON, отмена анализа и сохранение несохранённого
  документа при ошибке новой схемы.
- Все шесть реальных normal/Classic XDAT Essence/Japan/Korea прошли побайтовый
  и JSON-roundtrip с ленивой загрузкой.
- Во всех десяти измерительных запусках совпали порядок кандидатов,
  совместимость и размеры неразобранных хвостов.

Клиентские файлы и исходные локальные отчёты в эту документацию не включены.
