# Кнопка Test: компоненты и текущая проверка

## Новый прогон ненулевых указателей

Этап завершён в согласованном объёме. Legacy Gracia/HF исключены из требований
поддержки указателей: в проверенных Core отсутствуют native-экспорты PtrProperty.
Репликацию указателей пока не реализуем; запрет компилятора остаётся.

Исправленный комплект с GetFloat прошёл на Korean/Japan: **25 PASS / 0 FAIL / 0 SKIP**.
Build и хеши установленных файлов проверены; отчёты сохранены. Новый снимок
Japan подтверждает кнопку и итог. Для Korean подтверждение нового результата
есть в отчёте; нового снимка в прежнем каталоге нет. Подтверждены два нажатия,
но отдельных первых отчётов для сравнения не предоставлено.

### История подготовки проверки

Modern runner теперь использует два native `GFxValue`, а не только нулевое
хранилище. Он проверяет создание владельцев, разные ненулевые `pValue`,
копирование и обнуление копий без изменения владельцев. Ожидаемый итог нового
комплекта Korean/Japan: 25 PASS / 0 FAIL / 0 SKIP; подтверждение ещё требуется.
Первый комплект дал 23 PASS / 2 FAIL / 0 SKIP: native GetInt вернул нули.
Следующая версия использует AllocGFxValue/DeallocGFxValue, как исходные UI-скрипты,
и отдельно выводит признаки ненулевого/различающегося адреса. Ожидания 73/91
сохранены; прежние ошибки не переименованы в PASS или SKIP.
Вторая версия подтвердила ненулевые разные адреса, но получила 22 PASS / 1 FAIL.
Разбор native-кода показал: SetInt пишет GFx Number, для которого нужен GetFloat,
а не GetInt. В текущей версии getter исправлен; ожидаемые числа остались 73/91.
После каждого из двух нажатий Test сохранить `System/test.txt` отдельно и
снимок итогов. Если выполнение остановится на native-операции, последний
`RUN` в отчёте укажет участок; также сохранить клиентский лог.

Legacy-набор не получает pointer-объявлений: проверенные Gracia/HF не экспортируют
native PtrProperty. Их поддержка потребует отдельного runtime-адаптера.

## Клиентская проверка Sort этапа 5

Modern runner дополнен пустым и одноэлементным массивами: каждый получатель
должен вычисляться один раз, comparator не должен вызываться, значение 73
в одноэлементном массиве должно сохраняться. Ожидаемый итог Korean/Japan:
21 PASS, 0 FAIL, 1 SKIP. Для Gracia/High Five ожидается 12 PASS, 0 FAIL, 2 SKIP.
Клиентский прогон подтверждён на всех четырёх профилях: итоговые отчёты совпали
с указанными значениями, Build и хешами установленных комплектов. Все четыре
скриншота подтверждают размещение кнопки и итог. Два нажатия подтверждены
пользователем; отдельных первых отчётов нет для побайтового сравнения.

В изолированной копии клиента установить соответствующий комплект, запустить
клиент без сервера и нажать Test дважды. После каждого нажатия сохранить отдельную
копию `System/test.txt`; приложить снимок кнопки и итогов. Проверить привязку
Build и хешей установленного комплекта через `verify_client_report.py`.
Прежние отчёты этапа 4 не подтверждают новые Sort-проверки.

## Проверенные pointer-комплекты этапа 4

Новые сборки этапа 4 компилируются на всех четырёх профилях. Modern-набор добавляет
три проверки указателей: нулевое хранилище, locals/value/out/return и индексное
присваивание нуля. Сравнения выполняются через `PointerEqual`. Подтверждённый итог:
19 PASS, 0 FAIL, 1 SKIP; пропуск относится к ненулевым значениям в клиенте.
Legacy прошёл прежние 12 PASS, 0 FAIL, 2 SKIP.

Все четыре сборки прошли клиентский прогон и привязку отчётов к установленным
артефактам. Снимки Japan/Korean/Gracia подтверждают кнопку и итог; для High Five
проверен отчёт. Пользователь подтвердил два нажатия. Сохранён итоговый отчёт,
но отдельных первых отчётов нет для побайтового сравнения.

Для повторной проверки используйте отдельную
копию соответствующего клиента и четыре файла из `candidate/System`. Запустите
клиент без входа на сервер, нажмите Test, сохраните `System/test.txt` и снимок
экрана с итогом. Нажмите повторно и сохраните второй отчёт. При ошибке загрузки
сохраните её текст и клиентский лог. Далее проверьте отчёты и установленные файлы
через `verify_client_report.py`; старые отчёты к новой сборке не подходят.

Остальные подтверждённые клиентские результаты ниже относятся к предыдущим
расширенным комплектам. Этап 4 закрыт для описанного поддержанного поднабора;
ненулевые клиентские указатели и legacy-поддержка указателей остаются SKIP.

Новый тестовый интерфейс разрабатывается отдельно от прежней замены Credit.
Сценарий `build.py` пока относится к прежнему комплекту. Не используйте его как
универсальный сборщик четырёх новых профилей.

| `prepare_profile.py` | Сквозная подготовка четырёх профилей из оригиналов и подготовленного SDK |
| `compile_candidate.py` | Изолированная компиляция тестового Interface |
| `package_candidate.py` | Упаковка с проверкой профилей и хешей |
| `verify_client_report.py` | Проверка отчёта и хешей установленных файлов |
| `script_patch.py` | Обработчик Test с сохранением прежнего поведения остальных кнопок |
| `scripts/CompilerTestRunner.uc` | Базовые исполняемые проверки и запись отчёта |
| `scripts_modern/CompilerSortTestRunner.uc` | Дополнительные проверки клиентского Sort |

устанавливаются автоматически в клиент.

## Проверка профиля

```powershell
py -3 test_interfaces/profiles.py --profile korean `
  --client-system "<ORIGINAL_SYSTEM>" `
  --library "uExplorer/build/Release/uexplorer_core.dll" `
  --out "test_interfaces/local/profile.json"
```

Доступные имена: `gracia`, `high_five`, `japan`, `korean`. Имя профиля не заменяет
проверку хешей и ABI. Для резервного каталога, содержащего только часть файлов,
сначала подготовьте отдельную копию с соответствующими зависимостями.

## Разметка обычного окна

Для Japan согласована отдельная панель на экране входа. Экспериментальный режим
`--login-overlay --window UIEasyLoginWnd --login-button loginButton` со схемой
`essence_native.XDAT` создаёт `CompilerTestWnd` в `LoginState`: кнопка Test и поле
результата справа снизу. Исходное окно используется как шаблон; новая панель имеет
собственный класс из `scripts_japan`. Видимость и выполнение проверены в клиенте.
Сборщик принимает `--profile japan`. Оригинальные Japan и Korean содержат одинаковые
семь значений `Engine.Actor.EL2ObjectType` в одинаковом порядке, поэтому оба используют
компиляторный enum-профиль с историческим именем `korea290`. NWindow SDK для Japan
должен быть подготовлен из японского пакета: корейский не содержит всех его типов.

Для Gracia и High Five согласовано размещение Test нижним пунктом правого
нижнего меню, где находятся Credit и Options. Используйте `--menu-bottom`,
`--window LoginMenuWnd`, `--login-button btnReplay` и схему `ct24.XDAT` для
Gracia либо `ct26.XDAT` для High Five. В этом режиме последний пункт служит
шаблоном, шаг строк определяется из меню, высота окна увеличивается на одну
строку. Проверка обратимости удаляет Test и восстанавливает исходную высоту.
Внешний вид и обработчик проверены в обоих legacy-клиентах.

```powershell
py -3 test_interfaces/ui_patch.py --input "<ORIGINAL_SYSTEM>/Interface.xdat" `
  --schema korea_native.XDAT --window LogIn --login-button Btn_Login `
  --out "test_interfaces/local/layout/Interface.xdat"
```

Инструмент использует собранный модуль редактора `_interface_core` и встроенные
схемы. Он копирует оформление кнопки входа, задаёт текст Test и относительную
привязку слева с промежутком. Затем проверяет повторную сериализацию и точное
восстановление оригинала после удаления новой кнопки.

Это только XDAT-разметка. Для GFx-элементов операция неприменима: кнопка может
находиться внутри Flash-ресурса. Успешная сериализация не подтверждает внешний
вид в запущенном клиенте.

## Обработчик

```powershell
py -3 test_interfaces/script_patch.py --input "<EXPORTED_CLASSES>/Login.uc" `
  --profile korean --build-id "<SOURCE_HASH>" --client-sort `
  --out "test_interfaces/local/source/Login.uc"
```

Вместо условного значения `--build-id` передайте хеш или короткий идентификатор
сборки без пробелов. Исходник должен быть свежим UTF-8 экспортом с одним обычным
`OnClickButton(string)` на уровне класса. Инструмент не предназначен для
произвольных вручную изменённых исходников или обработчиков внутри состояний.

Прежний обработчик переименовывается, а новый направляет к нему все кнопки, кроме
`Btn_CompilerTest`. Для Test создаётся экземпляр тестового класса, устанавливается
флаг выполнения, показываются начало и итог. Повторное нажатие во время проверки
не запускает ещё один набор. Выполнение синхронное; промежуточный экранный текст
может отрисоваться только после возврата управления UI.

При компиляции также нужны `ExtensionL2API.uc`, базовый тестовый класс и, для
`--client-sort`, современный подкласс. Опция генератора исходника сама по себе
не включает поддержку Sort в компиляторе. Не включайте современный подкласс
в пакет неподдерживаемого клиентского профиля.

## Файл результатов

### Привязка результата к установленным артефактам

```powershell
py -3 test_interfaces/verify_client_report.py `
  --manifest "<CANDIDATE>/manifest.json" --system "<TEST_CLIENT>/System" `
  --out "test_interfaces/local/verified-report.json"
```

Проверка читает фактические четыре файла клиента, сверяет SHA256 с манифестом,
профиль и Build из `test.txt`, структуру строк и итоговые счётчики. Создаёт новый
JSON с хешем отчёта, манифеста, установленными хешами и отдельными результатами.
Выход должен находиться вне System. FAIL сохраняется в JSON и даёт ненулевой код;
несовпадение файлов, чужой Build или незавершённый отчёт отклоняются.
Это проверка файлов на диске после прогона, а не доказательство состава модулей
в памяти процесса. Скрипт не меняет клиент и не заменяет SKIP на PASS.
Матрица текущего покрытия находится в `COVERAGE.md`.

Результаты пишутся в `test.txt` рядом с ExtensionL2.dll. В установленном комплекте
DLL должна находиться в `System`, поэтому файл будет `System/test.txt`, независимо
от текущего рабочего каталога процесса. Каждое нажатие начинает новый отчёт.

- `Profile` и `Build` определяют профиль и идентификатор тестовых исходников.
- `RUN` сохраняется перед выполнением проверки.
- `PASS` / `FAIL` содержат ожидаемое и фактическое значение.
- `SKIP` содержит причину отсутствия проверки.
- `TOTAL` содержит счётчики.

Каждая запись сохраняет весь накопленный отчёт через WriteTextFile с flush.
При ошибке файла набор останавливается и возвращает сообщение. Если клиент
аварийно завершился во время теста, последняя сохранённая строка RUN помогает
определить выполнявшуюся проверку. Отчёт не читает поля авторизации.

Начальный набор проверяет native INT64, арифметику INT64, enum-конверсию,
byte-to-enum, пропуск optional-массива и чтение строкового отчёта. Современный
подкласс добавляет порядок Sort, вызовы делегата и однократное вычисление
получателя. Операции указателей пока отмечены SKIP. Это ещё не полное покрытие
всех возможностей компилятора.

## Сборка кандидата

Для полного процесса используйте `prepare_profile.py` по инструкции
`PROFILE_PIPELINE.md`. Ниже описаны отдельные стадии на примере Korean.

### Полная компиляция из подготовленных входов

```powershell
py -3 test_interfaces/compile_candidate.py `
  --sources "<EXPORTED_INTERFACE_CLASSES>" `
  --sdk "<MATCHING_COMPILER_SYSTEM>" `
  --tools "<UCC64_BUILD>" `
  --layout "<VERIFIED_LAYOUT_DIRECTORY>" `
  --native "<VERIFIED_NATIVE_DIRECTORY>" `
  --out test_interfaces/local/korean-automated-build
```

Все аргументы обязательны. `--sources` содержит свежий UTF-8 экспорт оригинального
Interface без тестовых классов. `--sdk` — согласованное окружение компилятора с
Core.u, Engine.u, NWindow.u. Сборщик создаёт собственный INI для загрузки этих
зависимостей и компиляции Interface. `--tools` содержит
ucc64.exe и Ucc64Bridge.dll. `--layout` содержит Interface.xdat и Interface.json,
`--native` — report.json и проверенные файлы в client. Их подготовка описана выше
и в инструкции native-профилей. Поддерживаются все четыре проверенных профиля.

Инструмент создаёт новый каталог под `test_interfaces/local`, добавляет API и
тестовые классы, формирует обработчик, записывает исходники в UTF-16 и запускает
изолированный компилятор с опциями выбранного профиля. Существующий Interface.u
из SDK не копируется. Лимит компиляции — 600 секунд. Ошибки и тайм-аут дают
ненулевой код; результаты находятся в `compile/result.json` и `compile/compile.log`.

`inputs.json` фиксирует именованные SHA256 исходников, SDK, инструментов,
генераторов и список опций. Хеш этих данных становится Build в runtime-отчёте.
После успешной компиляции `candidate/` собирается с проверкой хешей компаньонов.
Хеш итогового пакета хранится в манифесте отдельно: совпадение входов само по себе
не доказывает побайтовую детерминированность выходного пакета.

Доступен выбор `--profile gracia|high_five|korean|japan` (по умолчанию Korean).
Legacy-адаптеры используют `LoginMenuWnd` и базовый runner без Sort; современные
опции компилятора для них выключены. Полные сборки прошли: Gracia — ноль ошибок
и три предупреждения, High Five — ноль ошибок и 34 предупреждения. Расширенные
клиентские наборы прошли: 12 PASS, 0 FAIL, 2 SKIP (Sort и указатели).
Для экспорта из неполной резервной папки Gracia нужны соответствующие Engine.u
и NWindow.u из System: одного Core.u недостаточно для восстановления типов.
Параметр `dependencies` API uExplorer принимает каталоги, а не отдельные `.u`.
Ошибка `Class Actor Member Owner problem: Script=60 C++=64` до разбора исходников
означает несовместимость SDK-пакетов с native-структурой компилятора. Требуется
согласованный SDK; подмена полей исходного клиентского Actor для обхода ошибки
не является проверкой совместимости.

### Упаковка уже скомпилированного результата

После успешных отдельных проверок выполните:

```powershell
py -3 test_interfaces/package_candidate.py `
  --compile-dir test_interfaces/local/korean-click-compile `
  --layout-dir test_interfaces/local/korean-test-layout `
  --native-dir test_interfaces/local/automated-native/korean `
  --out test_interfaces/local/korean-test-candidate
```

Все аргументы обязательны. Выходной каталог должен быть новым и находиться вне
входных каталогов. Сборщик проверяет статусы и SHA256 артефактов до копирования,
затем повторно проверяет копии. В комплект входят `System` с четырьмя файлами,
`manifest.json` с хешами и границами проверки, `README_RU.md` с шагами запуска и
отката. Упаковщик сверяет соответствие схемы, native-профиля и размещения кнопки.
Ошибки входных отчётов или хешей завершают работу с ненулевым кодом.

Полная сборка Korean с обработчиком завершена: ноль ошибок, 60 предупреждений;
Japan — ноль ошибок, 65 предупреждений. Клиентские расширенные наборы обоих
профилей прошли: 16 PASS, 0 FAIL, 1 SKIP (указатели).

## Оставшиеся проверки

Все четыре профиля прошли расширенный набор и повторное нажатие. Проверены
размещение кнопки, экранный итог, запись файла и соответствие установленным хешам.
Полная подготовка из оригиналов также прошла на четырёх профилях.

Это не полное покрытие компилятора. Остаток по типам проверок перечислен в
`COVERAGE.md`; указатели остаются SKIP. Подготовка SDK — явный отдельный вход.
Новые клиенты требуют исследования адаптера. Проверка отказа записи в полном
клиенте исключена из согласованного плана; native-тесты ошибок DLL сохраняются.
