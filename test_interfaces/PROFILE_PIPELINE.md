# Подготовка полного тестового комплекта

`prepare_profile.py` объединяет обнаружение известного Core, экспорт оригинального
Interface, проверку native-комплекта, изменение XDAT, компиляцию и упаковку.
Все операции записи выполняются в новом каталоге под `test_interfaces/local`.

## Запуск

Нужны Windows Python с модулем редактора `_interface_core`, собранные uExplorer,
ucc64 и ExtensionL2 с EXE native-проверок. Запускайте из корня репозитория:

```powershell
py -3 test_interfaces/prepare_profile.py `
  --originals "<CLEAN_BACKUP>" `
  --dependencies "<MATCHING_SYSTEM>" `
  --sdk "<PREPARED_COMPILER_SYSTEM>" `
  --tools "<UCC64_BUILD>" `
  --native-build "<EXTENSION_BUILD>" `
  --library "<UEXPLORER_CORE_DLL>" `
  --out test_interfaces/local/full-profile
```

Все аргументы обязательны:

- `--originals`: оригинальные Core.dll, Core.u, Interface.u и Interface.xdat.
- `--dependencies`: соответствующие Engine/NWindow и DLL зависимостей. При наличии
  одноимённых пакетов в originals приоритет имеет originals.
- `--sdk`: уже подготовленный SDK компилятора. Это не каталог оригинального клиента.
- `--tools`: ucc64.exe и Ucc64Bridge.dll.
- `--native-build`: ExtensionL2.dll, client_link_probe.exe, extension_probe.exe.
- `--library`: DLL библиотеки uExplorer для Python соответствующей разрядности.
- `--out`: новый каталог вне всех входов.

## Стадии и результаты

1. Core определяется по native-каталогу; выбирается один из четырёх UI-адаптеров.
2. Проверяются зависимости и экспортируются все классы Interface. Partial/failed
   останавливают процесс.
3. Создаётся native-копия, проверяются загрузчик и VM.
4. XDAT проходит проверку сериализации и точного отката изменений.
5. В новом окружении компилируется Interface с API, тестами и обработчиком.
6. Комплект собирается в `build/candidate` с манифестом хешей и инструкцией отката.

`pipeline.json` содержит стадию, хеши входов, обнаруженный профиль и общий статус.
Логи стадий и экспорт лежат рядом. Ошибка даёт ненулевой код и сохраняет неуспешную
стадию. Неизвестный Core получает диагностику без патча и выполнения native-кода.
`completed=true` означает успешную подготовку, а не запуск в полном клиенте.

Полные процессы Gracia, High Five, Korean и Japan проверены от оригиналов до комплекта. Повторная сборка
с теми же входами сохранила Build и побайтовые XDAT/DLL. Interface совпал во всех
байтах, кроме 16-байтового GUID пакета. Поэтому хеш итогового файла может меняться
при одинаковом Build; манифест всегда должен соответствовать конкретному выходу.

## SDK и ограничения

SDK готовится отдельно: профиль клиента не определяет автоматически ABI
компилятора. Используйте согласованные Core/Engine и NWindow нужного клиента.
Для Japan проверена сборка NWindow из оригинального пакета; применение Korean
NWindow приводит к отсутствующим типам. Совпадение enum Engine Japan/Korean
проверено отдельно и позволяет применять исторический профиль `korea290`.

Поле `original_files` фиксирует входы, но имя профиля по Core не доказывает, что
произвольный Interface относится к той же сборке. Используйте чистые согласованные
резервные копии и проверяйте входные хеши. Исходные пути могут присутствовать в
локальных отчётах экспортера; такие отчёты не предназначены для публикации.

## Новый адаптер

Сначала исследуйте ABI и зарегистрируйте native-профиль по инструкции DLL.
Затем подтвердите схему XDAT, класс обработчика и режим UI. Добавьте соответствие
в `ADAPTERS`, компиляторный профиль и согласование профилей упаковщика. Проверьте
обратимость XDAT, полную компиляцию, native-исполнение, запуск клиента и Test.
Одного совпадения имени или нового хеша недостаточно для утверждения поддержки.

Проверка после установки выполняется `verify_client_report.py`, как описано в
`TEST_RUNNER.md`. Клиентская проверка отказа записи исключена; отдельные native-
проверки файловых ошибок остаются частью набора DLL.
