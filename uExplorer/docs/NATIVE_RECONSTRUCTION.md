# Восстановление базовых пакетов и native-контрактов

uExplorer восстанавливает исходники и предоставляет независимые метаданные
для проверки компилятора. Код native DLL не восстанавливается. Совпадение
деклараций, успешная компиляция и запуск клиента — отдельные виды доказательств.

## Порядок деклараций

Поля классов, структур и состояний обходятся по сериализованной цепочке
Children/Next. Порядок exports не является порядком native-полей. Циклы,
неверные владельцы и пропущенные поля приводят к `partial`, а не к успешному
восстановлению с предполагаемым порядком.

Скрытое поле `__Name__Delegate` восстанавливается декларацией соответствующего
delegate в позиции этого поля. Повторная декларация функции не выводится.
Порядок зависимых структур по-прежнему определяется зависимостями их типов.
Доступ функций сохраняется из flags. Переопределение родительского состояния
с тем же именем выводится без недопустимого `extends` на собственное имя.

## Приведения типов

`EX_MetaCast` восстанавливается как `class<T>(value)`, отдельно от
`EX_DynamicCast`, который выводится как `T(value)`. Подмена метакласса
объектным приведением меняет тип результата и мешает повторной компиляции,
в частности присваиванию `class<Pawn>` в Controller.SetPawnClass.
Синтетическая проверка входит в generation; Linux и Windows Release проходят
8/8 тестов. Повторное восстановление 364 классов Engine завершено без partial.

## Модификаторы функций и состояний

Флаг native latent-функции сохраняется как `latent`, а редактируемое состояние
выводится как `state()`. Потеря этих модификаторов меняет метаданные при повторной
компиляции. Проверки входят в generation и states; Linux и Windows Release
проходят 8/8 тестов.

Восстановление классов сохраняет `safereplace`, `nativereplication`, `placeable`,
`editinlinenew` и `collapsecategories`. Отрицательные модификаторы выводятся,
когда требуется отключить соответствующий унаследованный признак.
Для свойств сохраняются `input`, `export`, `travel`, `editconstarray`,
`editinline`, `editinlineuse`, `editinlinenotify`, `edfindable` и `deprecated`.
Некорректные или неподдержанные сочетания editinline-флагов приводят к partial.
Значения флагов независимо проверены компиляцией собственных примеров в SDK.

## Объекты в defaultproperties

Прямой вызов родительской функции (`final_call`) может ссылаться на другой
пакет. Сравнение символов учитывает и пакет, и индекс экспорта: совпадение
индексов в разных пакетах не означает совпадения функций. Потеря `super` при
восстановлении такого вызова превращает его в виртуальный вызов и может вызвать
бесконечную рекурсию. Регрессия проверяет базовую функцию из другого пакета
с тем же числовым индексом, что и переопределение.

Операция API `object` принимает `object_id` или путь `object` и восстанавливает
tagged-свойства отдельного экспортированного экземпляра по схеме его класса.
Результат сохраняет `path`, `class`, `outer`, `flags`, текст `properties` и
статус. Владельцем может быть пакет, класс или другой экземпляр; операция не
преобразует эту связь во вложенный `Begin Object`. Неизвестные свойства,
неподдержанный заголовок и native-хвост дают partial с исходными байтами.
Это интерфейс восстановления данных, а не доказательство сборки объектного
пакета или новый синтаксис SDK.

Name-литералы и пути объектов экранируют апостроф, обратную косую черту и
управляющие символы с учётом одинарного разделителя. Это относится к значениям
по умолчанию, структурам, массивам и выражениям байткода. Имя из одного
апострофа должно восстанавливаться как `'\''`, а не как незакрытый литерал.

Для nonfinite float-значений в defaults используется расширение openUCC
`__FloatBits("FFFFFFFF")`: восемь шестнадцатеричных цифр задают точные биты
IEEE-754. Оно сохраняет payload NaN и знак бесконечности без преобразования в
JSON null или десятичное число. Обрабатываются скалярные значения, элементы
массивов, поля структур и компоненты Vector. Конечные числа сохраняют прежнюю
десятичную запись. Это расширение исходного формата openUCC, а не синтаксис SDK;
nonfinite значения в выражениях байткода остаются отдельным ограничением.
Все восемь затронутых классов LineageEffect2/LineageEffect3 восстанавливаются
полностью и компилируются openUCC. Независимая сверка подтверждает точные биты
13 nonfinite значений и полное покрытие затронутых свойств массивов/структур;
полная проверка пакетов выполняется отдельно.

Объекты, владельцем которых является класс, восстанавливаются в блоки
`Begin Object Class=... Name=...` со значениями свойств. Ссылки на объекты
сохраняют полный путь. Проверяется полное чтение tagged-свойств: неизвестный
native-хвост приводит к partial, а не к его потере. Типы подобъектов добавляются
в зависимости исходного класса. SDK-пример подтверждает восстановление типа,
владельца и двух переопределённых значений.
Динамические массивы внутри структур defaults сохраняют порядок элементов;
отрицательные и чрезмерные размеры, неразрешённые типы и лишние байты отклоняются.
Корпус LineageSceneInfo восстанавливает 145 классов и 1 731 подобъект без partial.

Вложенность владельцев-экземпляров пока отклоняется. SDK трактует вложенный
`Begin Object` иначе: внутренний объект получает владельцем класс, поэтому
обычная вложенная запись не доказывает сохранение исходной цепочки Outer.

## Отчёт метаданных

Запрос CLI/C API:

```json
{"operation":"metadata","path":"original/Core.u"}
```

Отчёт не загружает DLL и не зависит от компилятора. `result.schema_version`
равен 1. Поля:

- `owners`: классы, структуры, состояния и функции; упорядоченные пути полей,
  superclass, export flags, а также соответствующие виду владельца flags.
- `properties`: типы, размерности, flags, категории, ссылки и replication offsets.
- `enumerations` и `constants`: пути и значения перечислений/констант.
- Для функций: native index, precedence и replication offset.
- `imports`: происхождение ссылок и наличие соответствующих локальных exports.
- `objects`: инвентаризация остальных объектов; payload явно обозначен `opaque`.
- `issues`: ошибки чтения и цепочек. При их наличии `status` равен `partial`.

`native_class_candidate` означает импорт класса Core.Class из собственного
пакета, которому не соответствует локальный export. Это свидетельство для
исследования native-типа, а не доказательство его иерархии или размера.
`external_unchecked` означает, что внешняя ссылка в этом отчёте не разрешалась.
`local_export_matches` содержит идентификаторы exports только для диагностики;
между разными сборками следует сравнивать пути и содержимое метаданных.

## Границы проверки

Отчёт не вычисляет смещения native-памяти, не восстанавливает отсутствующее
наследование и пока не декодирует граф default subobjects. Параметры функций
и результаты нужно сравнивать отдельно от локальных переменных и добавленных
декомпилятором вспомогательных функций.

Для пересборки Core/Engine компилятору необходим отдельный режим оригинального
пакета-образца: собственные классы разрешаются в новые exports, а подтверждённые
native-типы сохраняют необходимые связи с существующей DLL. Отчёт uExplorer
не снимает эту обязанность с компилятора.

## Проверки

CTest `layout` использует намеренно различающиеся порядки exports и field chains,
проверяет delegate storage, локальные/native-кандидатные импорты, циклы, чужих
владельцев и неполные цепочки. Остальные синтетические fixtures формируют
реальные цепочки владельцев перед декомпиляцией; цепочки параметров функций
остаются явными, включая отрицательные проверки.

Отдельные Linux Release- и Windows x64 Release-сборки проходят все восемь
CTest-проверок, включая `layout`. Это результат синтетических проверок;
проверка клиентского корпуса фиксируется отдельно.

Для оригинальных Core, Engine, NWindow и Interface корейского профиля отчёты
`metadata` Linux- и Windows-сборок совпадают целиком. Все четыре отчёта имеют
статус `complete` и пустой список issues; хеши входных пакетов не изменились.
Этот результат подтверждает чтение метаданных, но не пересборку Core/Engine.

Прямое восстановление этих четырёх пакетов даёт 1 294 класса (8 Core, 364 Engine,
140 NWindow, 782 Interface) без partial и без дополнительной перестановки
деклараций. Независимый аудит оригиналов не сообщает ошибок. NWindow и Interface
компилируются из нового вывода без внешнего исправления доступа и порядка полей;
аудит результатов также не сообщает ошибок. Порядок и метаданные свойств
классов/структур совпадают с оригиналами.

Более широкий отчёт сохраняет нерешённые различия компилятора: восемь флагов
параметров NWindow, отличающиеся export flags функций обоих пакетов и 14 ссылок
super функций Interface. В Interface дополнительно присутствует 301 helper.
Нельзя сводить эти результаты к утверждению о полном совпадении метаданных.

При дальнейшей проверке Core исправлены дополнительные потери восстановления:
модификатор `skip` параметров (`0x200`), `editconst` свойств (`0x20000`) и
определение class transient по биту `0x8`, а не `0x80`. Проверки этих случаев
проходят в Linux и Windows вместе со всеми восемью CTest-тестами.

С обновлённым компилятором все восемь классов Core корейского профиля собраны.
Аудит оригинала/результата не сообщает ошибок; проверенные метаданные 235
владельцев и сигнатуры функций совпадают. Также совпадают четыре перечисления,
восемь констант и литеральные defaults после нормализации порядка присваиваний
и неявного нулевого индекса статического массива. Отдельная клиентская проверка
нового Core с оригинальными Engine/NWindow/Interface подтвердила экран входа
и штатный выход с кодом 0 при ожидании 120 секунд. Хеши system восстановлены,
внешняя инвентаризация не обнаружила изменений. Проверка игрового мира и сети
этим результатом не покрывается.

## Enum defaults

Defaults классов для ByteProperty со ссылкой на enum выводятся именем значения,
как и вложенные struct defaults. Числовой вывод не обеспечивает корректного
повторного импорта: изолированный SDK-тест с `Choice=1` компилируется без ошибки,
но не сохраняет ненулевой default; `Choice=ChoiceOne` сохраняет байт 1.
Неизвестный enum или индекс за пределами его значений отмечается как `partial`.
Синтетический тест проверяет символическое значение и отклонение неверного
индекса. Блокер `Actor.DrawType` выявлен при пересборке Engine после прохождения
объявлений всех 364 классов.
Обновлённые Linux Release- и Windows x64 Release-сборки проходят все восемь
CTest-проверок, включая новый случай enum defaults.

Проверка клиентского корпуса выполняется отдельно в приватном рабочем каталоге:
хеши оригиналов → metadata/audit → восстановление → сборка → сравнение →
восстановимый клиентский запуск. Игровые исходники и результаты экспериментов
не включаются в репозиторий.
