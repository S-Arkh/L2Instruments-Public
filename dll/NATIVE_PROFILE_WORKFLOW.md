# Подготовка DLL для клиентского профиля

## Что проверяет этот процесс

Сценарий `tools/prepare_native_profile.py` определяет известный профиль Core.dll,
создаёт отдельную копию окружения, применяет проверенный адаптер загрузки и
исполняет проверки загрузчика и native-функций. Оригинальные файлы не заменяются.

Полученный комплект содержит только Core.dll и ExtensionL2.dll. Он **не является
готовым тестовым интерфейсом**: пакет ExtensionL2.u, Interface.u, размещение кнопки
Test и клиентские сценарии проверяются отдельно.

## Компоненты

| Файл | Назначение |
|---|---|
| `core_profiles.json` | Хеши оригиналов, адреса экспортов, признаки кода и особенности строкового ABI |
| `tools/core_profiles.py` | Анализ Core и генерация заголовка профилей |
| `src/client_profile.h` | Автоматически сгенерированные данные для DLL; вручную не редактировать |
| `src/client_abi.h` | Проверенные структуры и соглашения вызова VM |
| `src/extension_runtime.cpp` | Выбор профиля, проверка экспортов, регистрация native-функций |
| `src/extension_api.h` | Адаптеры аргументов и возвращаемых значений |
| `src/extensionL2.cpp` | Реализации функций и список `L2_NATIVE` |
| `tools/patch_core.py` | Создание новой Core с импортом ExtensionL2 и обёрткой точки входа |
| `tools/prepare_native_profile.py` | Автоматическая подготовка и проверка native-комплекта |
| `tests/client_link_probe.cpp` | Загрузка Core и соответствующей Engine |
| `tests/client_abi_probe.cpp` | Диагностика загруженного кода и ограниченные проверки VM |
| `tests/extension_probe.cpp` | Полные тесты расширения через клиентскую VM |

## Сборка

Из корня репозитория, в среде Windows с MSVC и CMake:

```powershell
cmake -S dll -B dll/build -A Win32
cmake --build dll/build --config Release
```

`generate_core_profiles` автоматически обновляет заголовок из JSON. Текущий
адаптер рассчитан на x86. Совпадение названия клиента не определяет совместимость.

## Анализ оригинала

```powershell
py -3 dll/tools/core_profiles.py analyze "<ORIGINAL_SYSTEM>/Core.dll" --report "<LOCAL_REPORT>.json"
```

Отчёт анализа показывает профиль, отсутствующие экспорты, адреса, признаки кода и
оставшиеся проверки ABI. Самостоятельный отчёт этого скрипта содержит исходный
путь и предназначен для локального использования.

У некоторых клиентов машинный код после загрузки отличается от содержимого
файла. Поле `code` хранит признаки файла, `loaded_step_code` — проверенную
последовательность загруженной FFrame::Step. Их нельзя подменять друг другом.

## Автоматическая подготовка

```powershell
py -3 dll/tools/prepare_native_profile.py `
  --core "<CLEAN_BACKUP>/Core.dll" `
  --dependencies "<MATCHING_SYSTEM>" `
  --native-build "dll/build/Release" `
  --out "dll/local/prepared-client"
```

Все четыре аргумента обязательны:

- `--core`: чистый оригинал Core.dll известного профиля.
- `--dependencies`: соответствующие ему Engine.dll и остальные зависимости.
- `--native-build`: собранная DLL и EXE проверок.
- `--out`: новый каталог вне входных каталогов.

Сценарий создаёт:

- `System/`: изолированные зависимости, патченную Core, DLL и EXE проверок;
- `loader.log`, `vm.log`: локальные результаты испытаний;
- `report.json`: профиль, хеши инструментов и выходных файлов, результаты;
- `client/`: Core.dll и ExtensionL2.dll после успешных проверок.

Логи могут содержать диагностические сведения окружения; не публикуйте их без
проверки. Сценарий не изменяет установленный клиент и не копирует туда комплект.

Код завершения 0 означает успех native-проверок. Ошибка аргументов даёт код 2;
ошибка подготовки или проверки — ненулевой код с диагностикой. В отчёте
`native_bundle_verified` становится true только после обоих успешных прогонов.
Поля `client_ui_tested` и `package_compilation_tested` остаются false.

## Как устроена загрузка

Патчер сохраняет исходные секции, экспорты и тела функций. Он добавляет импорт
ExtensionL2Attach и обёртку точки входа. Сначала выполняется исходная инициализация
Core, затем при подключении процесса регистрируются native-функции.

DLL проверяет адреса экспортов и загруженную сигнатуру Step для выбранного профиля.
Перед регистрацией проверяется весь список индексов: занятый чужой индекс не
перезаписывается. Повторное подключение той же DLL допускается.

EXE проверки и ExtensionL2.dll размещаются рядом намеренно: Windows ищет DLL в
каталоге EXE раньше каталога, указанного SetDllDirectory. Разные пути могут привести
к загрузке двух копий расширения и конфликту регистрации.

## Диагностика и новый профиль

1. Проверьте чистоту Core и соответствие зависимостей.
2. Запустите анализ. Для неизвестного хеша автоматическая подготовка сохраняет
   отчёт и прекращается без патча.
3. Проверьте архитектуру, экспорты, таблицу native-функций и код после загрузки.
4. На изолированной копии используйте `client_abi_probe.exe`:
   без опции — осмотр; `--vm-literals` — int/INT64; `--vm-native` — также вызов
   временного обработчика в свободном слоте и восстановление этого слота.
5. Подтвердите строковый ABI и полный набор `extension_probe`, затем адаптер
   автозагрузки и совместную загрузку Engine.
6. Добавьте профиль и соответствующие доказательства проверок. Одного нового
   хеша недостаточно. `loader_patch_verified` отражает отдельную проверку загрузчика.
7. Перегенерируйте заголовок, пересоберите DLL и повторите автоматический процесс.

Код 183 при подключении означает конфликт регистрации; проверьте уже установленные
расширения и пути загруженных DLL. Успех loader-проверки не доказывает ABI или работу
интерфейса. Успех VM-тестов не доказывает выполнение всех игровых сценариев.

Перед ручной установкой полного клиентского комплекта сохраните оригинальные
файлы. Для отката восстановите согласованные оригиналы; не смешивайте Core,
Engine и пакеты разных сборок. Сам сценарий подготовки установки не выполняет.
