# Поддержка Core: известные профили и новые кандидаты

## Что является источником данных

`core_profiles.json` хранит проверенные SHA256 оригинальных Core, RVA обязательных
экспортов, образцы машинного кода, идентификатор ABI и размер GNatives.
`tools/core_profiles.py` использует этот каталог в Python и генерирует
`src/client_profile.h` для C++. Заголовок не редактируется вручную.
Генерация включена в CMake и MinGW-сборку. Для CMake требуется Python 3.

На диске проверяются SHA256, экспортные RVA и образцы машинного кода.
При подключении DLL проверяются RVA, relocation-free префикс FFrame::Step
и доступность native-слотов. Полный SHA256 дискового файла не используется
как хеш загруженного образа: загрузчик изменяет IAT и применяет релокации.

Сейчас одобрены `client_b3fb9af3`, `clear_hf_0677e909` и
`gracia_epilogue_0941cac5`.
Изменения адаптера требуют повторной сборки DLL и повторной проверки профилей.

Gracia Epilogue использует 16-битные строки с экспортами `PBG` (`unsigned short`),
HF — `PB_W` (`wchar_t`). Поле `wide_char_type` каталога выбирает имена экспортов
`appThrowf` и присваивания FString в генерируемом заголовке. Размер символа
остаётся 16 бит. Комплект `dist/profiles/Gracia_epilogue` прошёл loader/VM-проверки
на оригинальной и патченной Core. Это проверка Core-расширения; браузерный UI и
Engine texture ABI имеют отдельный профиль в `../gameAddWebWithD3D9/client_profiles.json`.

## Автоматическая подготовка известного профиля

Все команды выполняются из каталога `rebuild/dll`.

```powershell
.\build.ps1
$ClientSystem = Read-Host 'Полный путь к system целевого клиента HF (используется далее)'
.\prepare_extension.ps1 -Destination extension-verified-new -ClientCore ..\..\Clear_hf\Core.dll -ClientSystem $ClientSystem
```

`-ClientCore` указывает оригинальную Core, даже если в установленном клиенте уже
стоит патч. `-ClientSystem` указывает именно тот полный клиент, который запускается.
Каталог назначения должен быть новым. После изменения профилей используйте
свежесобранные DLL и инструменты: прежние файлы `dist` не обновляются автоматически.

Последовательность:

1. Проверка обычных PE-импортов к выбранной Core.
2. Генерация UC из метаданных DLL, компиляция и проверка пакета/байткода.
3. Создание патченной Core и комплекта `client`.
4. Сверка готовой Core с результатом патча выбранного оригинала.
5. Создание временного изолированного каталога зависимостей и probe-программ.
6. Повторное получение метаданных из готовой DLL и проверка готового UC.
7. Loader Core+Engine и VM-probe с оригинальной Core (`manual`).
8. Loader Core+Engine и VM-probe с готовой Core (`patched`).
9. Проверка неизменности входных файлов и запись `client/bundle.json`.

Каждый EXE запускается отдельным процессом с таймаутом. Логи остаются в
`client/validation`. При ошибке комплект не получает успешный manifest.
Регрессионный VM-probe проверяет функции 4000..4009, файловый ввод/вывод и вызов из UCC;
новый несовместимый ABI требует адаптации и расширения этого probe.

`bundle.json` содержит хеши Core/ExtensionL2.dll/ExtensionL2.u, целевых потребителей
Core (включая Engine и l2.exe), каталога профилей, probe-инструментов, байткода,
результаты импортов и выполнения. Это локальный отчёт воспроизводимости,
не цифровая подпись и не доказательство запуска всей игры.

### Повторная проверка уже подготовленного комплекта

Если manifest ещё не создан:

```powershell
py -3 tools/validate_bundle.py ..\..\Clear_hf\Core.dll extension-verified-new/client --system $ClientSystem --tools build/Release --bytecode extension-verified-new/compiled-call.bin
```

На Linux добавляется `--wine /полный/путь/к/wine`; WINEPREFIX и окружение
задаются вызывающим процессом. Предполагается стандартное отображение диска Z:.
Валидация не перезаписывает существующий `bundle.json`: для новой проверки
создавайте новый комплект. Исходная игра используется только как источник файлов;
пробы исполняют копии в системном временном каталоге.

## Проверка установленного комплекта

После копирования трёх файлов из `client` в игровой `system`:

```powershell
py -3 tools/check_installation.py $ClientSystem --manifest extension-verified-new/client/bundle.json --report installation-check.json
```

`files_match: true` означает совпадение всех перечисленных файлов с проверенным
комплектом и целевым клиентом. Отсутствующий или заменённый файл даёт код выхода 1
и запись в `mismatches`. Инструмент ничего не устанавливает и не исправляет.

Отдельный раздел `resources` проверяет стандартные соседние каталоги
Textures/SysTextures/Maps/StaticMeshes/Animations/Sounds и два характерных пакета HF.
`conventional_layout_present: false` — предупреждение о расположении ресурсов,
а не автоматический запрет: пользовательские Paths в INI не декодируются.
Код выхода отражает совпадение файлов, не эту эвристику. Проверка не оценивает
полноту/содержимое всех ресурсов и не запускает игру.

## Неизвестная Core: анализ без допуска к патчу

```powershell
py -3 tools/core_profiles.py analyze "D:\OtherClient\system\Core.dll" --report core-candidate.json
```

Отчёт содержит SHA256, экспортные RVA, 16-байтовые образцы функций, PE-секции,
проверки размещения кода и таблицы, совпадение префикса Step и список вопросов ABI.
Для неизвестного файла `approved_profile` равен `null`, имя кандидата — `UNREVIEWED`.
Команда не меняет ни Core, ни каталог профилей. Совпадение всех эвристик
не разрешает патч: одинаковые экспорты не гарантируют одинаковые структуры.

### Включение нового профиля разработчиком

1. Сохранить оригинальные Core и Engine целевого клиента и отчёт кандидата.
2. Проверить дизассемблирование GRegisterNative/FFrame::Step/execUndefined,
   размер и инициализацию GNatives, layout FFrame, calling conventions и INT64.
   При отличиях сначала доработать адаптер и регрессионные тесты.
3. Только после проверки добавить запись кандидата с осмысленным именем в
   `core_profiles.json`. Это явное одобрение разработчиком, не автоматическое обучение.
4. Пересобрать DLL и инструменты; прогнать тесты прежних профилей и новую полную
   подготовку на целевом клиенте. На этапе разработки запись ещё не означает
   готовность профиля к распространению.
5. Проверить запуск полного клиента и вызов native-функций в игре, записать
   результат. При неуспехе не публиковать новый профиль как поддерживаемый.

Генератор намеренно отклоняет отличающийся префикс Step: под такой вариант
нужно явно расширить проверку/адаптер, а не только вставить другой хеш в JSON.

## Проверки разработчика

```powershell
py -3 tools/core_profiles.py generate --check
py -3 -m unittest discover -s tests -p "test_*.py"
```

Обычный запуск выполняет статические тесты и пропускает реальную интеграцию,
пока не заданы `EXTENSION_TEST_TOOLS` (каталог свежих EXE/DLL) и
`EXTENSION_TEST_BYTECODE` (проверенный compiled-call.bin). На Linux также задаётся
`EXTENSION_TEST_WINE`. Интеграционный тест создаёт временный комплект Clear HF
и выполняет всю цепочку `validate_bundle.py`, включая обе пары loader/VM.
Для новой версии API задайте `EXTENSION_TEST_PACKAGE` с соответствующим
ExtensionL2.u (например, test_interfaces/result/ExtensionL2.u); старый dist-пакет
по умолчанию содержит только исходные семь функций.
