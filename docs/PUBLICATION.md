# Публикация и обновление

Репозиторий имеет один корень и одну папку `.github/workflows`.
Имена и соседство компонентов сохранены для межкомпонентных зависимостей.

## GitHub

Создайте пустой репозиторий `L2Instruments` в своём GitHub-аккаунте.
После проверки `git status` из корня проекта:

```sh
git add .
git diff --cached --stat
git commit -m "Prepare unified L2Instruments source release"
git remote add origin https://github.com/YOUR_ACCOUNT/L2Instruments.git
git push -u origin main
```

CI собирает самостоятельные native-компоненты и запускает автономные тесты.
Игровые/интерактивные проверки выполняются отдельно с локальными клиентами.
Для Releases собирайте отдельные архивы компонентов, указывайте архитектуру,
версию, зависимости, SHA-256 и статус проверки. Сборка браузера без клиента
не является устанавливаемым UI-комплектом.

## Обновление из рабочего дерева

1. Сохранить текущую публикационную копию вне Git-дерева.
2. Снять SHA-256 исходного дерева до работы.
3. Переносить выбранные исходники и собственные материалы, сверяя изменения.
4. Сохранять публикационные адаптации: внешние пути `local_paths.py`,
   синтетические фикстуры, `Document.create` вместе с `Document.probe`,
   самостоятельную JSON-зависимость uExplorer, браузерные `--native-only`
   и инструменты подготовки SDK/входных данных.
5. Выполнить сборки/тесты и `python -B tools/check_publication.py`.
6. Обновить `docs/VALIDATION.md`; повторно проверить хеши исходного дерева.

Старые `prepare_sources.py` и `audit_publication.py` относились к двум отдельным
проектам и сохранены в резервной копии, вне нового репозитория.

## Исторические материалы

Отчёты разработки сохраняют даты, хеши и локальные пути прежней среды.
Упоминаемые `result`, `out`, `assets`, `workspace`, `inputs` и логи не поставляются
с исходниками. Результаты прежних тестов не означают проверку новой сборки.
