# UCC INT64 — расширение компилятора и сборка клиентского Interface

**Публикационная копия:** внешние пути и команды —
[SCRIPT_TOOLS](../docs/SCRIPT_TOOLS.md), [BUILD](../docs/BUILD.md).
UCC/SDK и клиентские пакеты подключаются отдельно. Каталоги и результаты
ниже относятся к исходному рабочему дереву разработки.

Рабочий каталог: **`rebuild/int64`**. Все команды ниже запускаются отсюда.
Работа с клиентскими DLL вынесена в **[../dll](../dll/README.md)**.
[Общая структура проекта](../README.md).

**[Справочник всех собственных скриптов](docs/SCRIPTS.md)** — назначение,
аргументы, примеры команд, выходные файлы и правила перезаписи.

Цель: писать числовой `int64` в UnrealScript и получать байткод,
совместимый с предоставленным клиентом Lineage II. В `.u` используется
`Core.Object.INT64`, но в пользовательском коде не нужны `Left/Right`.

## Текущий статус

Реализованы ABI-модуль и запускатель; **сквозная сборка тестового пакета прошла**
в Wine 9 x86 с оригинальным UCC и его MSVCR70/71. Проверены полученный байткод,
сериализованные defaultproperties, семь положительных/отрицательных сценариев
компиляции и выполнение числовых обработчиков непосредственно из клиентской DLL.
Подробности — `docs/VALIDATION.md`.

Готовые Windows x86 файлы находятся в **`dist/win32`**. Они собраны MinGW-w64.
Сборка в Windows, загрузка новых пакетов и все реализованные функции в игре проверены.
Для Scryde рабочая интеграция не получена либо исследования прекращены;
подтверждение игровых проверок на него не распространяется.

**Полный Interface.u собран: 253 класса, 3792 функции, 0 ошибок и 35 предупреждений.**
В клиентских пакетах обнаружен оригинальный ScriptText, поэтому повреждённая
декомпиляция заменена извлечёнными исходниками в отдельном workspace.

Основная инструкция: **[CLIENT_BUILD.md](CLIENT_BUILD.md)**.
Исходники всех EXE/DLL, сборка VS 2022 и сборка Int64Smoke.u:
**[BUILD_FROM_SOURCE.md](BUILD_FROM_SOURCE.md)**.
Пример совершенно новой native-функции, клиентской DLL и патча загрузки Core:
**[DLL: README.md](../dll/README.md)**.
Добавление собственных функций и C++ классов через `extensionL2.cpp`:
**[ADDING_NATIVE_FUNCTIONS.md](../dll/ADDING_NATIVE_FUNCTIONS.md)**.
Готовый клиентский пакет — `dist/client/Interface.u`, редактируемые исходники —
`workspace/Interface/Classes`, повторная сборка — `./build_interface.ps1`.

Оригинальные UCC.exe и DLL теперь находятся рядом: **`compiler/System`**.
Туда скопирован исходный комплект UCC; хеши записаны
в `compiler/manifest.json`. Подготовка рабочих каталогов использует эту локальную копию.

Модуль рассчитан на следующие точные бинарники:

| Файл | SHA256 |
|---|---|
| UCC.exe | `c68ba1ce0eab03af23b04dc1c991c3f1cc047a8a2076c6850e3071892806fb65` |
| Core.dll | `5bff274734cae994353a8c60f4bfe1087dbdd9aa3883c7b2a7eff6ea2f51dc7e` |
| Editor.dll | `d64995c1282956c6e9d67dd70715a69b5101331aa727a2d44b03e25fd7f2cd2e` |

Запускатель проверяет эти хеши перед запуском. Клиентскую DLL нельзя подставлять
вместо DLL компилятора. Исходные бинарники на диске модуль не патчит:
перехваты устанавливаются в памяти дочернего процесса UCC.

## Сборка под Visual Studio 2022

Нужны компоненты «Разработка классических приложений на C++», Windows SDK
и CMake. Для инструментов проверки — Python 3.10 или новее.
Исходники MinHook v1.3.4 включены в third_party/minhook; CMake использует их локально.

В PowerShell, в этом каталоге:

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A Win32
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Либо выполните `./build.ps1`. Результаты:

```text
build/Release/ucc64.exe
build/Release/Ucc64Bridge.dll
build/Release/int64_semantics_test.exe
build/Release/client_native_probe.exe
```

`ucc64.exe` и `Ucc64Bridge.dll` должны находиться рядом.
Для проверки готовой сборки из `dist/win32` установка CMake/Git не нужна.

## Первая проверка: изолированная сборка

Из каталога `rebuild/int64`:

```powershell
py -3 -m unittest discover -s tests -v
py -3 tools/prepare_smoke.py sandbox
& ./dist/win32/ucc64.exe --system ./sandbox/System make -NoBind 2>&1 | Tee-Object smoke.log
# Сразу после команды проверьте $LASTEXITCODE: ожидается 0.
py -3 tools/check_smoke.py sandbox/System/Int64Smoke.u
```

`prepare_smoke.py` создаёт НОВЫЙ каталог. Повторный запуск в существующий
каталог отклоняется. Для повторной полной проверки выберите `sandbox2`.
В копию переносятся DLL, необходимые пакеты и исходники `Core`; `Core.u`
пересобирается из исходников с имеющимися объявлениями `INT64` и операторов.
Исходная копия `compiler/System` при подготовке рабочих каталогов не изменяется.

В консоли должны появиться строки:

```text
[ucc64] Initialized; waiting for the compiler to load Editor.dll
[ucc64] Editor hooks installed (experimental INT64 bridge)
```

Сохраняйте `smoke.log` и `sandbox/System/UCC.log`, включая первую ошибку.
Если запускатель возвращает ненулевой код, его сообщения нужны целиком.

`check_smoke.py` проверяет токены преобразований, большие литералы,
native-индексы, вложенные cast, продвижение в float и сериализованные значения
`Amount` / `FixedValues`. Он не заменяет проверку исполнения полного пакета.
`Int64Probe.VerifyRuntime()` предназначен для вызова в целевом клиенте;
старый runtime компилятора не реализует клиентские INT64 native.

Полная регрессия компиляции (создаёт семь отдельных копий комплекта):

```powershell
py -3 tools/run_smoke.py sandbox-suite --launcher ./dist/win32/ucc64.exe
```

У исходного UCC обнаружена ошибка учёта диагностик: NAME_Error увеличивал
счётчик предупреждений, а процесс возвращал 0. Модуль исправляет счётчик
ошибок в памяти. Все шесть отрицательных тестов теперь возвращают код 1.

Декомпилированные файлы из u_files оставлены как исходные материалы.
Для сборки используется оригинальный ScriptText из пакетов — это устраняет
UnknownFunctionNNN и потерянные выражения без угадывания логики функций.

## Что реализовано в модуле

- Определение INT64 по полному имени `Core.Object.INT64`, а не по размеру структуры.
- Неявное расширение обычного `int`/`byte` в INT64 для скаляров.
- Неявное числовое преобразование INT64 в `float` для смешанных выражений
  (с обычной для float потерей точности больших целых).
- Явное `int64(expr)` в позиции выражения.
- Клиентские преобразования INT64 в `int`, `byte`, `bool`, `float`, `string`.
- Восстановление указателя структуры в результате неявного преобразования.
- Разбор десятичных/шестнадцатеричных литералов с проверкой диапазона signed 64-bit.
- Числовые скалярные значения INT64 в `defaultproperties` через перехват ImportText.
- Сохранение прежнего поведения 32-битных hex-масок вроде `0xffffffff`.
- Корректный ненулевой код завершения при диагностике NAME_Error.
- Ранжирование перегрузок: обычные byte/int выражения сохраняют 32-битную арифметику.
- Class flags localized, dynamicrecompile и nonativereplication.
- Символические поля Vehicle для совместимости API клиента с SDK компилятора.

Арифметические операторы берутся из существующих `native(400..413)` в Object.uc.
Автоматическое сужение в `int` не добавлено. Массивы не преобразуются целиком,
`out`-аргументы не подменяются временными преобразованными значениями.

Большие константы внутри байткода понижаются в `EX_PrimitiveCast(0x5e)` от
строковой константы с точной десятичной записью. В `.uc` остаётся обычное число.
Это выполняемое преобразование, а не нативный токен константы, поэтому имеет
стоимость при исполнении. Оно выбрано потому, что в клиентском SerializeExpr
не подтверждена обработка `0x46`, хотя обработчик исполнения такого токена есть.

Массивы, defaultproperties и именованные константы включены в успешно собранный
`smoke/Int64Smoke/Classes/Int64Probe.uc`. Defaultproperties и именованные константы
дополнительно проверены по содержимому `.u`. Исполнение массивов и полного
тестового класса в целевом игровом клиенте проверено.

## Исследование и эталоны

```powershell
py -3 tools/verify_profile.py
py -3 tools/ue2package.py ../../decompilled/client_dll/u_files/interface.u --function CalculatorWnd.GetOperand --function CalculatorWnd.SetNumeric --function CalculatorWnd.Calc
```

- `tools/ue2package.py`: читает оболочку Lineage2Ver111 и пакеты 123/37 и 126/0;
  различает компактные ссылки в файле и четырёхбайтовые ссылки в памяти байткода.
  Это ограниченный декодер, неизвестный opcode вызывает ошибку.
- `tools/verify_profile.py`: проверяет бинарники, экспортированные API, машинный
  вызов GetToken и извлекает регистрации INT64 из клиентской DLL.
- `reference/CalculatorWnd.int64.uc.inc`: восстановленные по оригинальному
  байткоду функции, не автоматическая замена всего CalculatorWnd.uc.
- `docs/ABI.md`: адреса и соглашения вызова для текущего профиля.

## Проверки в Windows и игре

1. Сборка и запуск в Windows проверены.
2. Загрузка Int64Smoke.u и вызов VerifyRuntime в целевом клиенте проверены.
3. Загрузка полного Interface.u и работа реализованных функций в игре проверены.

Базовый SDK, исходники и полная сборка интерфейса подготовлены. UWindow и ExScript
не являются прямыми зависимостями предоставленного Interface.u и не входят в
основную цепочку Core → Engine → NWindow → Interface.

Не переименовывайте этот запускатель в UCC.exe: он запускает оригинальный UCC
из указанного System и передаёт ему аргументы и код возврата.

## Сборка MinGW-w64

Альтернативная воспроизводимая процедура, которой получены готовые файлы:

```text
python tools/build_mingw.py --cc i686-w64-mingw32-gcc --cxx i686-w64-mingw32-g++ --out build-mingw
```

Скрипт проверяет локальные исходники MinHook и записывает `BUILDINFO.json` с хешами
артефактов. Для MinGW CMake также поддерживает 32-битный cross-toolchain.
